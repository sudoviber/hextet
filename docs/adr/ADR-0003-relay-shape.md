# ADR-0003：中继的形状（每对一端口、事件驱动升级、不自动选中继）

- 状态：已接受
- 日期：2026-08-11
- 相关：`docs/superpowers/specs/2026-08-06-hextet-design.md` §3 D5、
  `docs/protocol/relay.md`

## 背景

spec D5 要求：直连失败时经**用户自有节点**单跳转发加密的 WireGuard 包；默认关闭、
显式启用、状态透明、两端持续尝试直连升级。落地时有三处需要定型。

## 决策 1：每一对会话独占一个 UDP 端口

内核 WireGuard 自己持有 socket、发的是裸 WG 报文，中继无法要求它加上"这包发给谁"的
外层封装。所以中继只能按"包从哪来"解复用——而一个节点的多条中继流**共用同一个
WG socket**，源地址完全相同，中继无法区分该转给谁。

因此中继为每一对会话分配一个独立端口（`Register` → `RegisterAck{port}`），
在该 socket 上按源地址二选一。

**备选**：固定端口 + 按源地址解复用。放弃，因为它把"一个节点同时只能中继一条连接"
变成硬限制，而这个限制恰好会在用户最需要中继的时候（有多个难连的 peer）暴露。

代价：每对会话在中继上占一个 socket + 一个任务。用 256 会话上限约束（"别人的机器"
上的资源占用必须有明确上界）。

## 决策 2：直连升级是**事件驱动**的，不做定时盲试

`wg` 的每个 peer 只有一个 endpoint 字段。中继期间要试直连，只能把 endpoint 临时改成
直连候选；若直连不成，这段时间中继路径也是断的。**"边中继边探测直连"在内核 WireGuard
上做不到**（Tailscale 能做是因为它用用户态 WG，可以同时对多个地址发探测；hextet 要等
M4 引入 gotatun 才有这个可能）。

于是升级只在**有理由相信情况变了**时触发：会合层送来一个**新的**直连候选
（LAN 公告 / 阶段 D 的 gossip 转介 / 阶段 E 的 DHT）、或用户重启 daemon。
一旦直连握手成功，立刻注销中继会话。

**备选**：每 N 分钟中断中继试一轮直连。放弃（暂时），因为它让每条中继连接周期性地
断几秒，而收益只在"对端搬到了可直连的网络且本机毫无察觉"这一种情形里——
那正好是阶段 D 的 gossip 要解决的问题。

**这是对 spec D5「两端持续尝试直连升级」的一处偏离**，如实记录：
目前不"持续"尝试，只在有新证据时尝试。缺口与再评估条件：

- 阶段 D 落地后，对端换地址会主动广播，缺口基本被填上；
- 若真机使用中发现"该升级却没升级"，再加一个默认 ≥10min、可配、且在文档里
  写明中断代价的定时盲试，用新 ADR 覆盖本条。

## 决策 3：不自动挑选中继节点

中继节点必须在配置里显式标 `[[peers]] relay = true`，提供方也必须显式开
`[node] relay = true`。有多个候选中继时按配置顺序取第一个可用的，不做择优、
不做自动发现。

**理由**：行为可预测。中继会把流量的元数据（谁在跟谁通、多少量）交给中继节点，
"自动选一个"意味着用户无法预知自己的元数据会落到哪台机器上。Tailscale 的
Peer Relays 做自动化是因为它有中心控制面来编排；hextet 没有，也不想有。

## 透明性（不可协商）

- 走中继时 `punch_state` 是 `relayed` 而**不是** `connected`；
  `hextet status` 显示 `relayed via <名字>`。
- 进入中继一定伴随一条说明原因的 `info` 日志（"直连候选已轮换 N 轮仍无握手"），
  升级回直连同样有一条。
- 状态文件里有 `relay_via`，供 UI（M5）直接展示。

绝不静默降级：用户永远能看出这条连接经过了另一台机器。
