# ADR-0004：gossip 用签名 UDP 报文，而不是隧道内 QUIC

- 状态：已接受
- 日期：2026-08-12
- 相关：`docs/superpowers/specs/2026-08-06-hextet-design.md` §3 D4（控制平面）、
  `docs/protocol/gossip.md`

## 背景

设计 spec §3 D4 把 M3 起的控制面消息（endpoint 更新、成员增删、子网路由宣告）写成
「走 QUIC over WG 隧道内（quinn，连 overlay ULA 地址）的签名 gossip」。落地时要决定：
真的引入 quinn，还是用一个更轻的东西承载同样的「签名条目 + 单调 seq 收敛」。

## 决策

用**签名 UDP 报文**（`HXTG` 报文，overlay UDP 4197）承载 gossip，**不引入 quinn**。
每条目自带 ed25519 签名 + 单调 `seq`，线格式见 `docs/protocol/gossip.md`。

## 理由

1. **TLS 层在此是重复的。** 隧道内已经由 WireGuard 认证加密，QUIC 的 TLS 握手与记录
   层在这个内层完全多余——我们真正需要的是「条目不可伪造 + 分区重连后收敛」，
   那是 ed25519 签名 + LWW/单调 seq 的职责，不是 QUIC 的。
2. **gossip 是幂等的小状态同步，不是流。** 条目是「某 node 现在在哪 / 谁入网 / 谁被
   吊销」这类小而独立的声明。它不需要有序字节流、不需要拥塞控制、不需要连接生命周期；
   需要的是「重发几次、幂等接收」。为它引入 QUIC 是拿流语义去套状态同步。
3. **quinn ⇒ rustls ⇒ crypto provider 选择。** spec §13 已经把「rustls 默认
   aws-lc-rs 交叉编译坑」列为风险项。OpenWrt（M4）与 Android（M7）都要为这套依赖树
   付交叉编译与体积的代价，而它的产出我们基本用不上。
4. **报文小于 MTU 时，「发三次、幂等接收」比重传逻辑更简单也更可测。** 条目最大几百
   字节，远小于隧道 MTU（1400），没有分片问题；丢包靠 30s 周期重发 + 变化即发补足。
   这套语义能在纯逻辑里用单测钉住，而 QUIC 的连接状态机几乎无法在单测里穷举。

## 代价与再评估条件

- **没有流控/可靠投递**：大对象（例如将来某天要传「成员全量快照」超过 ~1 KB）会撞上
  单报文上限。若出现这种需求，再引入 QUIC 或自己做分片，届时用新 ADR 覆盖本条。
- **没有连接语义**：无法表达「这条消息是发给特定节点的私聊」。目前 gossip 全是对称
  广播，不需要私聊；将来需要点对点控制面时再评估。
