# hextet 自有节点中继（v1）

状态：已实现（`crates/core/src/relay.rs`、`crates/engine/src/relay_{server,client}.rs`、
`crates/engine/src/daemon.rs` 与本文档同步维护）。

## 它是什么，不是什么

**是**：双端入站全阻（典型场景：两侧都在中国移动蜂窝网络）时的逃生舱。用户把自己网络里
一个常电节点（家里的路由器 / 常开的 PC）显式声明为中继，两端经它单跳转发**已加密的**
WireGuard 包。

**不是**：项目方运营的中继基础设施。设计 spec §2 非目标 1 明确排除 DERP/TURN 舰队类
东西。中继只能是**这个网络里用户自己的节点**，默认关闭，须显式启用。

中继在 UDP 层透传：**不解密、不终结 WireGuard 会话、看不到流量内容**，端到端加密
完全不变。它能看到的只有"这两个 IPv6 地址之间有多少加密流量"。

## 三个先算清楚的约束

这三条决定了协议长什么样，不接受它们就会做出一个看起来能用、实际有坑的中继。

### C-0：控制帧必须自带 WireGuard 监听端口

控制帧是 daemon 从**它自己的** UDP socket 发出的——内核 WireGuard 独占监听端口
（默认 4193），用户态发不出那个端口的包。于是中继看到的控制帧源端口是个临时端口，
**不是**数据面会用的端口。

所以 `Register` 带上发送方的 WG 监听端口，中继把
`(控制帧源地址, 帧里的 WG 端口)` 记成这一侧的数据面地址。裸 WG 包的源地址与这条记录
精确相等（WG 从监听端口发包），回包也发到正确端口。

漏掉这一点的症状是"注册成功了但一个包都不通"。

### C-1：透明中继只能按「socket + 源地址」解复用 ⇒ 每对会话一个端口

内核 WireGuard 自己持有 socket、发的是裸 WG 报文，中继无法要求它加上"这包发给谁"的
外层封装。所以中继只能按"包从哪来"解复用——而一个节点的多条中继流**共用同一个
WG socket**，源地址完全相同。

因此中继为**每一对会话**分配一个独立 UDP 端口。会话 {A,B} 有自己的 `[R]:port_AB`，
A 与 B 都把对方的 endpoint 设成它；中继在该 socket 上按源地址二选一即可无歧义转发，
且 A 可以同时中继任意多个 peer（每个 peer 一个目标端口）。

这就是 `Register` 必须有 `RegisterAck` 回带端口的原因：客户端在拿到 ack 之前不知道该
把 endpoint 设成什么。

### C-2：内核 WG 一个 peer 只有一个 endpoint ⇒ 中继期间无法同时探测直连

`wg` 的每个 peer 只有一个 endpoint 字段。中继期间要试直连，只能把 endpoint 临时改成
直连候选；若直连不成，这段时间中继路径也是断的。**"边中继边探测直连"在内核 WireGuard
上做不到**（Tailscale 能做是因为它用用户态 WG，可以同时对多个地址发探测；hextet 要等
M4 引入 gotatun 后才有这个可能）。

因此直连升级是**事件驱动**的：只在有理由相信情况变了时才中断中继去试直连——会合层
送来一个**新的**直连候选（LAN 公告 / gossip 转介 / DHT），或用户重启 daemon。

实现上还有一处不显然：走在中继上时状态机是 `Connected`，而
`PeerFsm::set_candidates` 刻意**不打扰** `Connected` 的连接（一条正常工作的连接不该
因为"听到了新地址"被打断）。所以光把新候选塞进列表什么都不会发生——必须显式调用
`PeerFsm::retry_from(avoid = 中继 endpoint)` 让状态机离开中继去试一轮。
这个坑是三节点 E2E 抓出来的：中继本身通了，但升级那步永远超时。
代价要如实说明：**对端搬到了一个可直连的网络、而本机毫无察觉时不会自动升级**，
需要等一次会合层事件或手动重启。阶段 D 的 gossip 落地后这个缺口基本被填上。

## 端口

- 中继控制端口：`[node] relay_port`，默认 **4196**。只跑控制帧。
- 每对会话另有一个**内核分配的临时端口**，由 `RegisterAck` 告知。

## 控制帧线格式（96 字节定长，大端）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | magic | ASCII `HXTR` |
| 4 | 1 | version | 1 |
| 5 | 1 | kind | 1=Register, 2=RegisterAck, 3=Unregister |
| 6 | 2 | port | Register/Unregister：**发送方的 WG 监听端口**；RegisterAck：中继分配的会话端口 |
| 8 | 8 | seq | 发送时的 Unix 秒 |
| 16 | 32 | self_key | 发送方公钥 |
| 48 | 32 | peer_key | 这对会话另一端的公钥 |
| 80 | 16 | mac | `HMAC-SHA256(relay_key, bytes[0..80])` 截断前 16 字节 |

- `relay_key = HKDF-SHA256(salt="hextet-v1", ikm=network_key).expand("relay", 32)`
- MAC 校验用常量时间比较；解析顺序：长度 → magic → version → kind → **MAC** →
  公钥曲线点校验。长于 96 字节的数据报只看前 96 字节。
- `self_key == peer_key` 直接拒绝（自反射没有任何合法用途）。
- 会话键 = 两个公钥按字节序排序后的二元组，因此两端各自算出同一个键。
- `RegisterAck` **原样回带**请求里的 `self_key` / `peer_key`，客户端据此把 ack 与自己的
  请求配对。
- 冻结测试向量见 `crates/core/src/relay.rs::tests::frozen_wire_vector`。

## 数据平面：零封装

会话端口上收到的数据报**不以 `HXTR` 开头就是要转发的 WireGuard 包**，原样透传。

这条判据安全，因为 WireGuard 报文首 4 字节是小端 u32 的消息类型 1..=4
（`01 00 00 00`..`04 00 00 00`），与 ASCII `HXTR`（`48 58 54 52`）不可能相同。
`crates/core/src/relay.rs::tests::wireguard_headers_are_never_mistaken_for_relay_frames`
显式构造这 4 种首部并断言不被误认——判据错了会把 WG 包当控制帧丢掉，
或者更糟：把控制帧当数据转发出去。

在会话端口上收到的**控制帧一律丢弃**（不解析、更不转发）。

## 服务端行为契约

1. 只有 MAC 合法、`|seq − now| ≤ 300s`、且策略允许的 `Register` 能建/续会话；
   其余**静默丢弃**（不给探测者任何反馈）。
2. 一对会话的两侧地址都就位之前**不转发任何东西**（半开会话）。
3. 同一对会话的后续 `Register`（另一侧、或续期）返回**同一个**端口。
4. 一侧换了地址（换前缀）→ 它的下一次 `Register` 更新该侧地址，转发继续。
5. 会话数上限 256（每对占一个 socket 与一个任务）。达到上限时先清理过期会话，
   仍满则**拒绝新会话**，不驱逐已有会话。客户端会因收不到 ack 而超时，如实报告
   "中继不可用"。
6. 会话 TTL 180s（客户端每 30s 续期）；超时即关闭 socket 与任务。
7. 每对会话每秒最多转发 2000 个包（≈22 Mbps @1400B）。超限丢包，
   且**每窗口最多记一条** warn（每包一条日志本身就是放大攻击）。
8. 缓冲区 2048 字节；收到恰好填满缓冲区的数据报按"可能被截断"丢弃。
9. 绝不解析被转发数据报的内容，日志里绝不出现载荷。

## 策略

- `RelayPolicy::AnyMember`（默认）：任何持有本网络 network key 的成员都能用。
- `RelayPolicy::Allowlist`：只有列出的公钥能建会话。会话两侧**各自**校验，
  只放行一端时会话保持半开、不转发。

## 安全性

| 威胁 | 结果 |
|---|---|
| 非成员在别人的中继上建会话 | 挡住：没有 network key 就算不出合法 MAC |
| 重放旧的 `Register` | 挡住：±300s 窗口；重放当前帧只能续一条本就有效的会话 |
| 中继读取流量内容 | 做不到：转发的是 WireGuard 加密包，中继没有任何 peer 的私钥 |
| 中继看到什么 | 两个 IPv6 地址之间的流量大小与时间——**这是真实的元数据泄露**，所以中继只能是你自己的节点 |
| 中继篡改/丢弃流量 | 能做到（它在路径上）。篡改会被 WireGuard 的认证挡下（表现为丢包），丢弃则等价于链路故障——所以中继必须是你信任的机器 |
| 成员把中继当放大器 | 每会话包速上限 + 会话数上限 + 半开不转发；载荷不放大（1:1 转发） |
| 成员用中继反射到任意地址 | 挡住：目标地址只能是**另一侧注册过的**地址，且必须先通过 MAC 认证 |
| 恶意成员伪造中继控制帧（`Register`/`RegisterAck`/`Unregister`） | **能做到**：`relay_key` 由 network key 派生、全网共享，任何成员都能算出来；可把对端的 WG endpoint 指到错误地址（可用性破坏）、或替别的成员注册会话槽位。**不影响机密性**——WG 端到端加密不变，中继/伪造者都读不到内容。这是「任何成员都能用中继」（`RelayPolicy::AnyMember`）这一共享密钥模型的固有代价，属诚实边界：中继的可用性保证只对**非成员**成立，对**恶意的网络成员**不成立 |

## 客户端行为

- 直连候选**整整轮换 2 轮**仍无握手才注册中继（`RELAY_AFTER_ROUNDS`，≤8 候选 ×
  2.5s × 2 ≈ 最多 40s）。给足直连机会，又不让确实连不上的场景干等。
- 中继 endpoint 作为候选**排在最后，且预留一个名额**：直连候选再多也挤不掉它，
  否则"直连全不通"这个正好需要中继的场景反而轮不到中继。
- **会话一旦建立就把候选收窄到只剩中继**，直到出现"该升级回直连"的新证据。
  原因是两端各自按 2.5s 轮换，必须**同时**落在中继候选上才握得上手；掺着直连候选
  一起轮换会让两端反复错开——CI 上实测把收敛时间从约 7s 拖到 28s，且概率性更久。
  此刻那些直连候选刚刚被整整试过 2 轮全部失败，留在列表里没有价值。
- **中继 endpoint 绝不进端点缓存**：那个端口是中继临时分配的，会话一结束就失效。
  把它记成 `last_good` 只会让下次启动先去试一个死地址，还会污染"上次直连成功在哪"
  这个真正有用的信息。
- 每 30s 续期；注册失败后 60s 冷却再试（否则 `rounds` 每涨一轮就触发一次 5s 超时的
  注册，在中继不可达时变成持续刷日志）。
- 直连一活立刻 `Unregister`，让中继马上释放那对会话的 socket 与任务。
- 走中继时 `punch_state` 报 `relayed`（不是 `connected`），`status` 显示
  `relayed via <名字>`，且进入/离开中继各有一条说明原因的 `info` 日志。

设计决策（每对一端口、事件驱动升级、不自动选中继）见

## 验收

`scripts/netns-e2e-relay.sh`（CI job `e2e-relay`）：三个 netns 挂在同一 bridge 上，
nftables 掐断 A↔B 的单播直连、保留与 R 的路径，断言 A/B 经 R 中继连通
（`punch_state == "relayed"`、`relay_via == "r"`、endpoint 指向 R 的**临时**会话端口而
不是 4193/4196）、overlay 双向 ping 通、`status` 人类输出含 `relayed via r`；
随后解除阻断并给 B 加一个新地址，断言 A 在 30s 内升级为直连、`relay_via` 归空、
日志里有"已升级为直连"。
